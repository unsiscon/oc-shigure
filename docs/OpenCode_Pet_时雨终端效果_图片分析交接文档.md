# 2. 图片一：当前 OpenCode TUI 实际运行效果

## 2.1 直接可见的整体效果

当前角色位于 OpenCode 右侧栏中部，尺寸较小，属于典型终端侧栏宠物占位。

整体仍然可以识别出以下元素：

- 棕色长发；
- 蓝色眼睛；
- 红色领带或领结；
- 黑白制服；
- 双腿和深色鞋靴；
- 头部明显大于身体，采用 Q 版比例。

因此，当前版本并不是“完全无法识别”，基础人物轮廓已经存在。

但实际观感明显弱于参考图和预览图，主要问题分为两类：

1. **真实终端中出现了预览图里没有的灰白色噪点或半格块。**
2. **即使忽略噪点，当前低分辨率角色本身的造型和色块分配也比较粗糙。**

---

## 2.2 灰白噪点的具体视觉表现

在真实终端角色周围可以观察到大量浅灰色、灰白色或近白色的小矩形块。

这些块具有以下特征：

- 很多呈现出明显的横向半格形态；
- 分布不连续，不像有意设计的外轮廓；
- 主要出现在角色的透明边缘附近；
- 与头发、脸部、袖子、腿部和鞋子边缘交错；
- 部分灰白块似乎悬浮在角色轮廓外部；
- 它们破坏了轮廓的连续性，使人物看起来“毛糙”“闪烁”或“有白点”。

较明显的区域包括：

### 头部和发型附近

- 刘海和脸部交界处存在多处浅色块；
- 两侧头发轮廓外侧出现灰白小格；
- 头顶及侧发部分存在不属于棕色发块的浅色碎片。

### 面部附近

- 蓝眼、肤色和深色轮廓之间出现额外浅色间隔；
- 面部边缘不够干净，像被插入了一些浅灰像素。

### 手臂和衣袖附近

- 白色袖子周边出现额外的灰白色小块；
- 部分白块和真正的暖白衣服区域难以区分；
- 使手臂结构比预览图更碎。

### 腿部和鞋子附近

- 双腿、袜子和鞋靴附近可以看到零散浅色横条；
- 部分浅色块位于本应透明的角色外部。

---

## 2.3 这些灰白块不像正常美术细节

从视觉上看，这些灰白块与以下几类合理设计不一致：

- 不像稳定的高光，因为位置过于零散；
- 不像统一描边，因为没有连续包围角色；
- 不像衣服白边，因为大量白块位于透明外轮廓；
- 不像有意的像素抖动，因为预览图中并不存在同样的图案；
- 不像正常缩放后的锯齿，因为形状更接近终端半格单元。

因此，仅依据图片对照，可以较有把握地判断：

> 真实终端中的部分灰白块并不是 Agent 预览美术中的原始内容，而是在实际渲染或 TUI 集成阶段出现的额外视觉结果。

至于根因究竟是透明像素处理、前景/背景颜色继承、半块字符组合、TUI 主题背景，还是 ANSI 样式重置问题，仅凭图片不能完全确定，需要代码侧进一步排查。

# 3. 图片二：高精细度角色参考图

## 3.1 这张图提供的主要价值

该图展示了一个较完整、精细的 Q 版时雨像素形象。

视觉上较突出的特征包括：

- 大面积棕色长发；
- 长发左右自然下垂，而不是纯横向展开；
- 一侧有更明确的发束、编发或发饰结构；
- 大型蓝色眼睛；
- 脸部轮廓清晰；
- 红色发饰和红色领带形成识别重点；
- 黑白制服有完整肩部、衣身、裙摆和袖口结构；
- 腿、袜子、鞋靴层次分明；
- 头、躯干、裙摆、腿之间的比例关系清楚；
- 角色整体轮廓完整，不会出现“头发是一团、身体挂在下面”的感觉。

---

## 3.2 该参考图不适合直接缩成终端像素稿

这张图的精细度明显高于 24×24 或 16×16 逻辑像素画布能够承载的内容。

图中包含大量小尺度信息：

- 多层刘海；
- 发丝层次；
- 多档棕色阴影；
- 眼睛内部高光与深浅色；
- 服装细小白边；
- 袖口和手套细节；
- 裙摆褶皱；
- 腿部边缘与袜口；
- 鞋面高光；
- 红色饰品的小型结构。

如果将这些内容直接机械缩小到 24×24：

- 大量发丝会合并成不规则棕色块；
- 蓝眼内部细节会消失；
- 制服白边可能变成零散白点；
- 袖口和手臂可能融合；
- 腿、袜、鞋之间的层次可能坍缩；
- 红色领带容易变成一条过粗的竖向色带。

因此，这张图更适合用作：

- 角色身份参考；
- 发型轮廓参考；
- 颜色关系参考；
- 服装分区参考；
- 头身比例参考。

它不适合直接作为 24×24 终端 Sprite 的逐像素模板。

# 4. 图片三：不同尺寸与比例参考图

## 4.1 这张图反映出的关键规律

该图展示了同一角色在多个尺寸下的变化。

其中最有价值的观察不是“缩小后仍然很精细”，而是：

> 角色在尺寸变小时，细节数量减少，但主要结构关系没有丢失。

在较小版本中仍然可以看到：

- 头发外轮廓清晰；
- 脸部没有被头发完全吞没；
- 双眼仍然是独立的蓝色视觉中心；
- 红色领带仍存在，但没有压过整个身体；
- 白色衣服区域仍然属于衣领、袖口或衣身结构；
- 裙摆形状明确；
- 两条腿有足够宽度；
- 鞋子是完整的小型色块，而不是零散点；
- 身体虽然简化，但仍然有肩部—躯干—裙摆—腿的连续层级。

---

## 4.2 对当前终端稿最有参考价值的部分

这张图说明，低分辨率简化时可以主动删除：

- 发丝细节；
- 衣服褶皱；
- 眼睛内部复杂高光；
- 鞋面纹理；
- 小饰品的内部结构。

但应尽量保留：

- 头发的整体方向；
- 面部可见面积；
- 双眼位置；
- 红色重点色的位置和面积；
- 制服的黑白分区；
- 裙摆边界；
- 双腿与鞋子的完整结构；
- 一侧发束、编发或发饰带来的角色辨识度。

换言之，参考图的价值主要是“简化后仍保留什么”，而不是要求终端稿复现全部细节。

# 5. 图片四：Agent 生成的终端像素预览

## 5.1 预览图中的正面信息

该图展示了 idle、thinking、working、waiting、success、error、retry 等多个状态。

可以直接观察到：

- 角色的主要颜色已经统一；
- 棕发、肤色、蓝眼、红色领带、深色制服、白色衣物区域都存在；
- 多个状态大体保持同一基础轮廓；
- 动画变化主要围绕眼睛、刘海、手臂、身体倾斜、腿部位置展开；
- 该预览图中没有真实 TUI 截图里那些明显的灰白噪点；
- 图中黑色背景下的透明轮廓相对干净；
- 角色轮廓与真实 TUI 中的主要棕色、蓝色、红色、白色部分基本对应。

这说明：

> 当前终端截图中的白点问题，不宜简单归因于 Agent 的预览 Sprite 本身，因为预览图中并没有同样的白点图案。

---

## 5.2 预览图本身的主要美术问题

即使完全忽略真实终端里的白点，预览图本身仍有比较明显的低分辨率设计问题。

### 5.2.1 头发横向占比过大

角色头发在左右两侧大面积展开，形成很宽的棕色块。

结果是：

- 人物整体显得非常宽；
- 面部和身体被夹在头发中央；
- 发型更像一大团背景色，而不是自然下垂的长发；
- 头部的视觉重量过大；
- 身体显得更小、更弱。

对比高精细参考图，参考图的长发虽然体量大，但有明显向下流动的方向感；当前预览更接近横向铺开的棕色云团。

---

### 5.2.2 脸部信息不足

脸部被刘海、眼睛、白色衣物和深色轮廓挤压。

可见问题包括：

- 肤色区域过小；
- 眼睛虽然是蓝色，但眼睛与脸部的关系较拥挤；
- 鼻口信息基本不存在；
- 左右眼和刘海之间缺乏足够清晰的间隔；
- 面部容易被理解为多个颜色块，而不是完整的脸。

低分辨率不一定需要画出鼻子，但至少需要保证：

- 脸部轮廓完整；
- 两个眼睛的位置明确；
- 刘海不能过度切碎脸部。

---

### 5.2.3 白色袖子像两根竖直色条

当前两侧白色区域非常醒目。

视觉上更像：

- 两根垂直白柱；
- 两条从脸旁直接向下延伸的色带；
- 与身体缺少自然连接的白块。

它们不太像有弯曲关系的手臂或袖子。

这会导致：

- 身体结构被切成中间红色、两侧白色、外层棕色；
- 手臂动作不易理解；
- working、waiting 等状态之间的动作差异不够自然。

---

### 5.2.4 红色领带或领结面积过大

红色区域从脸部下方一直贯穿到身体下部。

在低分辨率下，它成为最强的中心色块。

结果是：

- 红色视觉权重高于脸部、制服和裙摆；
- 角色容易被概括成“棕色头发 + 两条白柱 + 一条红柱”；
- 红色作为识别重点是有效的，但当前面积和长度过大；
- 领带、胸口和裙摆之间的关系不够清楚。

---

### 5.2.5 躯干和裙摆的层次不清楚

当前身体区域主要由：

- 深色横条；
- 红色竖条；
- 少量深蓝或黑色块；
- 两侧白色块

组成。

可见问题：

- 肩部不明确；
- 胸口和腰部难以区分；
- 裙摆外轮廓较弱；
- 身体与头发下缘混在一起；
- 腿像直接从一条深色横线上伸出；
- 角色缺少完整的上身—裙摆—腿部过渡。

---

### 5.2.6 双腿过细、鞋子信息不足

双腿在很多帧中接近细长竖线。

鞋子虽然有红棕色，但面积较小、位置分散。

结果是：

- 下半身视觉重量不足；
- 大头和大头发压住了身体；
- 双腿难以支撑整个角色轮廓；
- 成功、重试等动作变化不容易通过腿部读出。

---

### 5.2.7 角色辨识度偏向“通用棕发制服女孩”

当前能够识别出的要素是：

- 棕色长发；
- 蓝眼；
- 黑白制服；
- 红色领带。

但更具体的时雨识别点不够强，例如：

- 一侧发型结构；
- 细辫或侧边发束；
- 红色发饰；
- 长发的落点；
- 制服领口的具体关系；
- 相对独特的轮廓不对称性。

因此，即使没有白点，当前稿仍然更接近通用 Q 版制服女孩，而不是明确的时雨终端 Sprite。

---

## 5.3 各状态之间的可读性

预览图中多个状态的变化比较细微。

### idle

- 两帧差别非常小；
- 主要是眼睛或刘海的一像素变化；
- 静态观看时不容易感知差异。

### thinking

- 眼睛和刘海位置略有变化；
- 由于基础脸部已经较拥挤，思考状态的变化不算明显。

### working

- 手臂向内收；
- 但白色袖子本身已经很像竖条，因此动作读感有限。

### waiting

- 手靠近中间；
- 与 working 的轮廓差别不够大。

### success

- 双腿或脚部上移；
- 由于腿部很细，动作更像脚部位置变化，不像明确的跳跃或开心。

### error

- 头部和肩部下降；
- 整体确实更低沉，但脸部信息仍然不足。

### retry

- 上半身轻微左右倾斜；
- 这是比较适合低分辨率的动作类型，因为轮廓整体变化比单个眼睛变化更容易被看见。

# 6. 四张图的交叉对照结论

## 6.1 当前问题不是单一问题

从对照结果看，当前最终效果一般，至少由两个相互独立的问题叠加造成：

### 问题 A：真实终端渲染与预览不一致

直接证据：

- `art-preview-regular.png` 中没有大量灰白噪点；
- 真实 OpenCode TUI 中出现了明显的灰白半格和横条；
- 额外白点主要位于透明轮廓附近。

这更接近渲染或 TUI 集成问题。

### 问题 B：低分辨率 Sprite 本身仍然不够成熟

直接证据：

- 即使只看无白点预览图，头发、脸、白袖、红领带、躯干、腿部之间的比例仍不理想；
- 与参考图相比，主要差距不只是像素数量，更是色块分配和轮廓设计；
- 当前简化结果没有充分保留时雨最具辨识度的结构。

这属于美术设计和低分辨率重构问题。

---

## 6.2 参考图过于精细，但不是无用

第二、第三张参考图确实比 24×24 终端稿精细很多。

因此，主开发 Agent 不应尝试：

- 直接复刻全部细节；
- 把高分辨率 PNG 自动缩到 24×24；
- 将所有服装、发丝和眼睛细节编码进终端矩阵。

但参考图仍然非常有价值，因为它明确提供了：

- 发型总体轮廓；
- 双眼与脸部比例；
- 红色重点色的合理面积；
- 白色和深色制服的分区；
- 裙摆、腿和鞋的完整结构；
- 在小尺寸下仍然需要保留的角色识别特征。

---

## 6.3 当前预览稿不是“因为像素太少所以必然不好看”

从第三张不同尺寸参考图可以看出：

- 尺寸变小并不必然导致结构崩溃；
- 小尺寸仍然可以维持清晰的头、脸、身体、裙摆和腿部关系；
- 关键在于低分辨率下重新设计，而不是从大图机械降采样。

因此，当前预览稿的问题不能完全归因于 24×24 上限。

更准确的说法是：

> 24×24 确实限制了细节，但当前像素预算还可以重新分配，仍有明显改进空间。

# 7. 配套像素数据与图片的关系

## 7.1 当前数据定义

`shigure-pixel-data.json` 和 `shigure-pixel-data.md` 中已经定义了：

- `.` 为透明像素；
- 多档棕色用于头发；
- 肤色；
- 两档蓝色用于眼睛；
- 深色用于制服；
- 暖白色用于制服白边；
- 红色用于领带或裙边；
- 黑色用于袜子；
- 红棕色用于鞋靴；
- 深色轮廓。

并提供了：

- 24×24 regular 矩阵；
- 16×16 compact 矩阵；
- idle、thinking、working、waiting、success、error、retry 的动作契约。

---

## 7.2 对图片分析的补充意义

由于主开发 Agent 没有多模态能力，它可以通过这些文件理解：

- 哪些字符代表透明；
- 哪些字符代表特定颜色；
- 每一行应该有多少逻辑像素；
- 每个状态允许改变什么，不允许改变什么。

但这些文件本身不能让 Agent理解：

- 最终角色是否好看；
- 白色块在真实终端里是否形成噪点；
- 头发是否太宽；
- 红色领带是否太抢眼；
- 袖子是否像两根白柱；
- 身体和腿部是否可读；
- 是否像时雨，还是像通用制服女孩。

本文主要补充的就是这些视觉信息。

# 8. 直接观察、较强推断与未确定事项

为了避免主开发 Agent 把视觉判断误当成已经验证的技术结论，这里区分三种可信度。

## 8.1 可以直接从图片确认

- 真实终端截图中存在大量灰白半格或横条；
- 预览图中没有同样的灰白噪点；
- 当前预览稿的头发横向面积很大；
- 白色袖子呈明显竖条形态；
- 红色领带面积偏大；
- 身体、裙摆和腿部结构不够清晰；
- 高精细参考图具有更明确的发型、脸部、制服和下半身结构；
- 不同尺寸参考图说明角色可以在缩小时保留主要结构。

## 8.2 基于对照的较强推断

- 灰白噪点大概率不是原始 Sprite 美术内容；
- 噪点可能发生在透明像素、半块配对、前景/背景颜色或 TUI 样式处理阶段；
- 预览器与真实 TUI 可能没有经过完全相同的最终渲染路径；
- 当前 Sprite 可能是根据复杂参考图过度压缩，而不是重新设计；
- 24×24 的像素预算分配存在优化空间。

## 8.3 仅凭图片无法确定

- 灰白块究竟由哪一段代码产生；
- 是否是 alpha、调色板、ANSI reset、终端主题、父容器背景或字符宽高问题；
- 预览器和实际 TUI 是否调用同一个 Renderer；
- 当前 PNG 是否参与运行时转换；
- 本地 Qwen-VL 是否能稳定识别半格噪点；
- TrueColor 是否已经启用；
- 当前终端字体、行高和字符宽高是否引入额外形变。

这些事项需要主开发 Agent通过代码、日志、最小测试和真实终端实验确认。

# 9. 供主开发 Agent 参考的视觉验收重点

以下内容不是强制工作流，仅作为图片分析后的验收参考。

## 9.1 渲染一致性

建议检查同一个 idle 帧在以下位置是否一致：

- 索引矩阵预览；
- 放大像素预览；
- 半块字符测试输出；
- OpenCode 侧栏真实 TUI。

核心验收点：

- 真实 TUI 不应出现预览中不存在的灰白块；
- 透明区域应保持为 TUI 原背景；
- 轮廓外不应产生额外浅色半格；
- 同一颜色索引不应在不同渲染路径中变成不同颜色。

---

## 9.2 美术结构

在不追求高精细复刻的情况下，建议重点观察：

- 头发是否有向下流动的轮廓，而不是只向两侧膨胀；
- 脸部肤色区域是否完整；
- 双蓝眼是否清楚分离；
- 白色区域是否像衣领和袖子，而不是两根白柱；
- 红色重点色是否适量；
- 上身、裙摆、腿、鞋是否具有连续结构；
- 一侧发束、发饰或细辫是否足够明显；
- 角色是否能被识别为时雨，而不仅是棕发制服女孩。

---

## 9.3 动画状态

低分辨率下，整体轮廓变化通常比单个像素变化更容易被察觉。

可重点观察：

- idle 两帧是否真的能看出呼吸或眨眼；
- thinking 与 idle 是否有足够差异；
- working 和 waiting 的手臂姿势是否容易区分；
- success 是否像成功或跳跃，而不是腿部错位；
- error 是否有明显低落轮廓；
- retry 的左右倾斜是否保持身体完整。

---

# 10. 简要参考建议

以下建议仅作为补充，不替代主开发 Agent规划。

1. 在继续重画角色前，先确认预览与真实 TUI 的白点差异是否来自 Renderer。
2. 可先固定一个 24×24 idle 帧进行视觉和渲染一致性验证。
3. 本地 Qwen2.5-VL Q4 更适合做“是否有白点、哪里不一致”的粗粒度视觉检查，不宜作为单像素美术裁决者。
4. 如果修复白点后角色仍不理想，再单独讨论 24×24 Sprite 的简化和重构。
5. 16×16 版本应独立设计，不宜由 24×24 自动缩放得到。

# 11. 最终结论

当前最终效果一般，不宜简单归因于“终端半块像素做不到”。

从四张图的对照来看：

- **真实终端出现了预览图中不存在的灰白噪点，说明渲染链路至少存在一个需要独立排查的问题。**
- **无白点预览稿本身也存在头发过宽、脸部过挤、白袖像竖条、红色领带过强、躯干和腿部不清晰、角色辨识度不足等问题。**
- **高精细参考图确实超出 24×24 能直接复刻的范围，但它仍然可以用于确定应保留的轮廓、比例和识别特征。**
- **不同尺寸参考图表明，小尺寸并不必然等于结构粗糙；关键是针对低分辨率重新设计。**

因此，当前问题应被理解为：

> “真实终端渲染不一致”与“低分辨率角色设计尚未成熟”两个问题叠加，而不是单纯的终端能力上限。
